# STM32C5 NUCLEO-C562RE Bare-Metal Projects (VS Code)

This repository provides register-level bare-metal driver and project templates targeting the **STM32C5 NUCLEO-C562RE** development board (Cortex-M33, `target/stm32u5x.cfg`). The GPIO and UART drivers are hand-coded against the STM32C5-compatible register map — no HAL, no CubeMX, no vendor device headers beyond CMSIS core (used only for NVIC interrupt control).

## Board & Hardware

| Item | Value |
|---|---|
| MCU | STM32C562RE (Cortex-M33, `cortex-m33` toolchain flag) |
| NUCLEO type | NUCLEO-C562RE |
| Flash base | `0x08000000` |
| RAM base | `0x20000000` |
| RCC base | `0x44020C00` |
| GPIO base | `0x42020000` (AHB2) |

### Onboard User LEDs (NUCLEO-C562RE)

| LED | Pin | Colour | Notes |
|---|---|---|---|
| LD1 | PA5 | Green | Only user LED; Arduino D13 |

## Folder Structure

```
STM32C5-NUCLEO-Projects/
├── Makefile                  # Generic build, flash, debug automation (GNU Make)
├── linker/                   # GCC linker scripts, shared by all modules (see "Memory layouts")
├── build/                    # generated by make, git-ignored: build/<PROJECT_DIR>/<Name>.elf/.bin/.hex/.map
├── tools/                    # seal.py, clear_tag.py, bl_upload.py, monitor.ps1, ci/ …
├── Drivers/                  # Register-level drivers, each also a standalone demo
│   ├── GPIO/                 # e.g. one module folder:
│   │   ├── module.mk         #   build wiring (library sources, dependencies, memory layout)
│   │   ├── inc/gpio.h        #   RCC_TypeDef, GPIO_ManualTypeDef, pin macros
│   │   └── src/              #   gpio.c, main.c, startup.c
│   ├── AES/ CRC/ DMA/ FDCAN/ HASH/ NVIC/ RNG/ SysTick/ UART/
│   ├── USB_CDC/              # USB CDC ACM (virtual COM port) on the USB-C user port — TinyUSB glue
│   ├── TinyUSB/              # git submodule: hathach/tinyusb (USB stack + CDC ACM class)
│   ├── stm32c5xx-dfp/        # git submodule: ST CMSIS device headers (needed by TinyUSB's ST port)
│   └── CMSIS_6/              # git submodule: Arm CMSIS core headers (core_cm33.h)
└── Projects/                 # Application-level projects (use the Drivers above)
    └── App_Demo/ Bootloader/ ECDSA/ FLASH/ RSA/ Root_of_Trust/
        Secure_Boot/ Secure_FW_Update/
```

## Architecture

Drivers follow **object-oriented C** style — each peripheral has a handle struct and a constructor:

```c
/* GPIO example */
GPIO_InitTypeDef led_init = { .Mode = GPIO_MODE_OUTPUT_PP, .Pull = GPIO_NOPULL,
                               .Speed = GPIO_SPEED_MEDIUM, .Pin = GPIO_PIN_7 };
GPIO_HandleTypeDef ld1;
GPIO_constructor(&ld1, GPIO_C, &led_init);   // enable clock + configure PC7
GPIO_TogglePin(&ld1, GPIO_PIN_7);            // toggle LD1 green

/* UART example */
USART_HandleType uart2;
USART_constructor(&uart2, USART_2, RX_AND_TX, __115200);
USART_WriteString(&uart2, "Hello\n");
```

CMSIS (`core_cm4.h`) is used **only** for `NVIC_SetPriority()` / `NVIC_EnableIRQ()`. All peripheral register access uses hand-defined structs (`RCC_TypeDef`, `GPIO_ManualTypeDef`, `USART_ManualType`) mapped directly to hardware addresses.

## Prerequisites

- **Clone with submodules** (TinyUSB, stm32c5xx-dfp, CMSIS_6 — used by `Drivers/USB_CDC`):
  `git clone --recurse-submodules --shallow-submodules <repo>`, or in an existing clone `make submodules`.
  `make submodules-update` moves them to the newest upstream commits (commit the result to pin them).
- **Line endings** are normalized by `.gitattributes` (LF in the repository), so Windows git and
  WSL/Linux git can both be used on the same working copy without every file showing as modified.
- **VS Code** (latest)
- **Cortex-Debug extension** (`marus25.cortex-debug`)
- **arm-none-eabi-gcc** toolchain (GCC 12+ recommended, add to PATH)
  - Linux: `sudo apt install gcc-arm-none-eabi`
  - Windows: download from [Arm Developer](https://developer.arm.com/downloads/-/gnu-rm)
  - Not on PATH? The Makefile falls back to the toolchain and `STM32_Programmer_CLI` bundled with
    **STM32CubeIDE** (`C:/ST/STM32CubeIDE_*`, also from WSL via `/mnt/c/ST/...`, or `/opt/st/stm32cubeide_*`).
    Point it elsewhere with `TOOLCHAIN_DIR=<toolchain>/bin` / `CUBE_PROG=<path>`.
- **OpenOCD** with STM32C5 target support (add to PATH)
- **GNU Make** (add to PATH — e.g. the one shipped with STM32CubeIDE, MSYS2 or Git-for-Windows)
- **ST-Link USB drivers** ([STSW-LINK009](https://www.st.com/en/development-tools/stsw-link009.html))

## Building

The build is plain **GNU Make + arm-none-eabi-gcc**.

```sh
# Show every target, variable and buildable PROJECT_DIR (same as 'make help')
make

# Build the PROJECT_DIR selected at the top of the Makefile
make build

# Build any other module
make build PROJECT_DIR=Drivers/GPIO
make build PROJECT_DIR=Projects/Secure_Boot
```

Output goes to `build/`, never into the source folders, named after the module:
`build/Projects/App_Demo/App_Demo.elf` / `.bin` / `.hex` / `.map` (objects in `…/obj/`). Only changed
files are recompiled. `make clean` removes the selected module's output, `make clean-all` all of
`build/`. `DEBUG=1` builds go to `build/debug/` so they never mix with the `-O2` objects.
Ready-made binaries of every module are attached to each CI run (see [Continuous integration](#continuous-integration)).

### Memory layouts (`linker/`)

All modules share one set of linker scripts. A module picks its layout with `LAYOUT` in its `module.mk`:

| `LAYOUT` | Script | Flash region | Used by |
|---|---|---|---|
| `standalone` (default) | `linker/standalone.ld` | `0x08000000`, all 512 KB | Driver demos, ECDSA, FLASH, RSA |
| `bootloader` | `linker/bootloader.ld` | `0x08000000`, 64 KB (sectors 0–7) | Bootloader, Secure_Boot |
| `app_slot` | `linker/app_slot.ld` | `0x08010000`, 176 KB (sectors 8–29) | App_Demo, Root_of_Trust, Secure_FW_Update |

The three scripts only define `MEMORY`. The addresses come from `linker/memory_map.ld` (the single
place they are defined) and the output sections from `linker/sections.ld`. `make flash` writes to the
layout's start address (`FLASH_ADDR`), and CI checks that it matches what the linker used.
`STACK_SIZE` (default `0x400`) sets the stack reserved by the linker; RSA uses `0x2000`.

Every image carries the record `IMGID:<module>` right after its vector table (`linker/image_id.c`).
`make read-flash` reads the flash over SWD — the MCU keeps running — and names what is programmed:

```text
0x08000000  Boot region : Bootloader
                          boot code — starts the active slot
                          same as build/Projects/Bootloader/Bootloader.bin
0x08010000  Active slot : App_Demo
                          CRC tag F440CDF7 OK — the bootloader starts it
                          same as build/Projects/App_Demo/App_Demo.bin
```

### Module wiring (`module.mk`)

`make build` builds the folder selected by `PROJECT_DIR`. The Makefile reads only that folder's
`module.mk` as the project, plus the `module.mk` of every module it lists in `DEPS`.

Each `module.mk` has two parts:

1. **Library interface** (always read), prefixed with the folder name — what other modules get
   when they list this one in their `DEPS`:

   | Variable | Meaning |
   |---|---|
   | `<Name>_SRC_C` | Library source(s) linked into dependents |
   | `<Name>_INC` | Library include directory |

2. **Standalone build** — an `ifeq ($(MODULE),<Name>)` block that only applies when this folder
   is `PROJECT_DIR`. It holds everything specific to building and uploading it:

   | Variable / content | Meaning |
   |---|---|
   | `DEPS` | Modules (folder names under `Drivers/` or `Projects/`) linked into this build |
   | `EXTRA_INCS` | Extra include-only directories |
   | `LAYOUT` | Memory layout: `standalone` (default), `bootloader` or `app_slot` |
   | `STACK_SIZE` | Stack reserved by the linker (default `0x400`) |
   | `POST_FLASH` | Commands run after `make flash` (optional) |
   | `MODULE_HELP` | Extra lines for `make help` (optional) |
   | targets, `CFLAGS +=` … | Project-specific targets (`bl-upload`, `seal-active`, …) and flags |

```make
# Drivers/UART/module.mk
UART_SRC_C := Drivers/UART/src/uart.c
UART_INC   := Drivers/UART/inc

ifeq ($(MODULE),UART)
DEPS := GPIO DMA
endif

# Projects/App_Demo/module.mk
ifeq ($(MODULE),App_Demo)
DEPS       := UART NVIC
LAYOUT     := app_slot
include tools/mk/active_slot.mk   # seal-active, restore-bootloader, clear CRC tag after flash
endif
```

Adding a module only means adding its folder with a `module.mk` (and `LAYOUT` if it is not
standalone). `NVIC` is always
linked (its `nvic.c` provides the IRQ handlers every vector table refers to). `make help` lists the
modules that will be linked and the targets the selected `module.mk` adds.

### Startup code

Each module's `startup.c` uses `_estack` / `__etext` / `__bss_start__` etc. from `linker/sections.ld`, places the vector table with `__attribute__((section(".isr_vector")))`, and does the `.data` copy / `.bss` zero-fill itself before calling `main()`.

**Overridable variables:**

| Variable | Default | Description |
|---|---|---|
| `PROJECT_DIR` | set at the top of `Makefile` | Module to build / flash |
| `TOOLCHAIN_DIR` | PATH, else STM32CubeIDE | Folder containing `arm-none-eabi-gcc` |
| `CUBE_PROG` | PATH, standalone install, else STM32CubeIDE | `STM32_Programmer_CLI` used by `flash` and the tools/ scripts |
| `FLASH_TOOL` | `cubeprog` | `cubeprog`, `openocd` or `stlink` |
| `DEBUG` | `0` | Use `1` for debugger-friendly codegen (`make debug` sets it) |
| `PORT` / `BAUD` | auto / `115200` | Serial port for `make monitor` / `make bl-upload` |
| `DEFAULT_PORT` | `COM5` / `/dev/ttyACM0` | UART port `make bl-upload` falls back to when no ST-LINK is detected |
| `LINK` | `auto` | `make bl-upload` link: `usb` (USB-C user port), `uart` (ST-LINK VCP) or `auto` (also `link=`) |
| `USBIPD` | `0` | `1` = WSL with the board's USB devices attached through usbipd |

## Flashing

Connect the NUCLEO board via USB (ST-Link), then:

```sh

```

## Bootloader (UART + USB)

Full guide with every upload command: [Projects/Bootloader/README.md](Projects/Bootloader/README.md).
How it works (block diagram, boot decision, protocol): [Projects/Bootloader/ARCHITECTURE.md](Projects/Bootloader/ARCHITECTURE.md).

`Projects/Bootloader` sits at `0x08000000` and boots the application in the active slot
(`0x08010000`, CRC-32 tag in sector 30). After every reset it waits 5 s (LD1 on) for an update —
10 s once a PC has enumerated its USB port:

| Entry | What happens |
|---|---|
| `u` on USART2 (ST-LINK VCP, PA2/PA3) | Update over UART |
| `u` on USB CDC (USB-C user connector, PA11/PA12) | Update over USB — opening the COM port re-sends `[BL] READY` and adds 3 s |
| B1 pressed in the window, or held during reset | Stay in the bootloader (LD1 blinks, `[BL] READY` every second) |
| 1200-baud touch on the application's USB port | App_Demo resets into the bootloader, which stays |
| Nothing | Verify tag + CRC + vector table, then jump to the application |

```sh
make flash PROJECT_DIR=Projects/Bootloader     # once, over SWD
make bl-upload                                 # build + upload Projects/App_Demo (LINK=auto)
make bl-upload LINK=usb                        # through the USB-C user connector (USB1)
make bl-upload LINK=uart PORT=COM4             # through the ST-LINK virtual COM port (USB0)
make bl-upload APP=path/to/app.bin             # a ready binary linked at 0x08010000
make bl-enter                                  # only put the board into the bootloader over USB1
make read-flash                                # name the bootloader + application in flash (USB0)
```

`LINK`, `PORT`, `APP` and `USBIPD` may also be written in lower case (`link=uart`). A link that is not
connected to this PC is an error — `LINK=uart` never falls back to USB, `LINK=usb` never to UART.

The bootloader's USB device is `C562 Bootloader CDC` (`CAFE:B0C5`), App_Demo's is `C562 App CDC`
(`CAFE:B0C6`) — TinyUSB test VID, development only. Each exists only while its program runs.
Integrity is a CRC-32 only — there is no authentication (see `Projects/Secure_Boot`).

### WSL2 + usbipd

WSL2 cannot see USB devices until they are attached with [usbipd-win](https://github.com/dorssel/usbipd-win).
Keep the **ST-LINK on Windows** (flashing, SWD reset and the Makefile use the Windows STM32CubeProgrammer)
and attach only the **USB-C user port** to WSL:

```powershell
# Windows, PowerShell as administrator — once
winget install usbipd
usbipd policy add --effect Allow --operation AutoBind --hardware-id CAFE:B0C5   # share it, even while unplugged
usbipd policy add --effect Allow --operation AutoBind --hardware-id CAFE:B0C6   # App_Demo's port

# Windows, normal PowerShell — every session, keep it running
usbipd list                               # BUSID of CAFE:B0C5 (hold B1 + RESET so it enumerates)
usbipd attach --wsl --busid <BUSID> --auto-attach --unplugged   # re-attaches after every reset
```

```sh
# WSL
sudo usermod -aG dialout $USER            # serial access to /dev/ttyACM*, then log in again
ls /dev/ttyACM*                           # appears while the bootloader runs
make bl-upload LINK=usb USBIPD=1
```

Without usbipd, `bl_upload.py` re-runs itself with the Windows Python and uses the COM ports directly.

## Continuous integration

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on GitHub-hosted runners for every push to
`main`, every pull request, and on demand (*Actions → CI → Run workflow*). Nothing runs on a local PC.

| Stage | What it checks |
|---|---|
| **Lint** | cppcheck on all module sources, ruff on `tools/` (`tools/ci/lint.sh`) |
| **Build** | Every folder with a `module.mk`, one job each, Arm GNU Toolchain 14.3.rel1 — any compiler warning fails |
| **Host tools** | `tools/bl_upload.py` against a simulated bootloader, Python 3.8 and 3.12 (`tools/tests/`) |
| **Verify** | Load address = linked FLASH region (from the map file) = `FLASH_ADDR`, region inside the chip, `.bin` = ELF, size fits the slot and the 512 KB chip, vector table (`tools/ci/verify_build.py`) |

Artifacts on each run: `fw-<module>` (ELF, BIN, HEX, map, build log) and `firmware-<commit>`, all images
plus a `manifest.json` (sizes, SHA-256, bootloader slot CRC-32). Flashing and bootloader uploads need the
board and stay manual tests.

Run the same checks locally:

```sh
tools/ci/lint.sh                                       # needs cppcheck + ruff
python3 -m unittest discover -s tools/tests -v         # needs pyserial
python3 tools/ci/verify_build.py build/Projects/App_Demo/App_Demo.elf 0x08010000   # after make build
```

## Debugging in VS Code

### GCC + Cortex-Debug (OpenOCD / ST-Link)

1. Ensure `.vscode/launch.json` targets Cortex-Debug with OpenOCD and ST-Link
2. Press `F5` or open **Run and Debug**
3. Set breakpoints and step through code normally

The **Debug: Active App (from Makefile)** configuration runs the `GCC: Build + Flash for Debug` task (`make debug`) first, which builds `PROJECT_DIR` with `DEBUG=1`, copies it to `build/debug/active.elf` and flashes it. Without VS Code:

```sh
make debug PROJECT_DIR=Drivers/GPIO
```

## Troubleshooting

- **Missing separator in Makefile** — ensure command lines use tabs, not spaces
- **Toolchain not found** — add `arm-none-eabi-gcc` and `openocd` to system PATH
- **Wrong LED pins** — check your board's user manual and update `Drivers/GPIO/src/main.c`
- **OpenOCD target not found** — ensure your OpenOCD installation includes `target/stm32u5x.cfg` (used by this repo's STM32C5 setup)
- **Breakpoints never hit** — most common causes:
   - Built a different project than the file you are editing. Check `PROJECT_DIR` in `Makefile` or pass `PROJECT_DIR=...` on the command.
   - Optimized build loaded. Use `make debug` (enforces debug-friendly options).
   - Breakpoint is hollow/unverified. Start debug first, then check it turns solid red.
